# S14 — Payment reminder notifications from Needs Attention: working notes

Supplementary to `current-feature.md` — same reasoning as `s10-invoice-creator.md`/`s11-dispute-assistant.md`/`s12-telegram-conversational.md`/`s13-payment-webhook-notification.md` before it. `docs/feature.md`'s `### S14` section is the source of truth for *what* this is; this file is scoped to *how* it gets built.

## How this started

Earlier this project, a "send reminder mail to overdue invoice customers" feature was explored in Plan Mode and explicitly abandoned mid-planning ("forget about this feature, do not implement it") — confirmed nothing survived into `docs/`. The owner later asked to build a version of this for real, with a specific shape: cover both overdue invoices *and* failed payments (the latter wasn't surfaced anywhere before), draft-then-review each as an editable email in the chat, individually sendable plus a "Send all" button, and explicitly simulated sending (log only, no real email).

## Three design decisions this story is built around

1. **One combined "Send Notification" trigger**, not per-row buttons — drafts everything currently overdue/failed in one tool call, so a single "Send all" in the resulting tile has one coherent batch to act on.
2. **Editing is local to the tile, not routed through the shared `editHint`/`focusSignal` mechanism.** That mechanism (shared by `InvoiceReviewCard`/`DisputeResponseCard`) is built for exactly one editable thing at a time, confirmed by reading `App.tsx` — no slot for "which of N items." `PaymentReminderCard` holds each draft's subject/body as local React state instead, since editing already-drafted text needs no LLM reasoning at all.
3. **Sending bypasses the LLM entirely and isn't pending-action-gated** (ADR-016). Once text is finalized, sending needs no reasoning, only logging a string — `POST /api/reminders/send` is called directly by the frontend. No confirm step either: unlike every money-moving action in this app, nothing real happens (no Stripe write, no real email), so ADR-006's guardrail has nothing to gate — the review-then-edit step in the tile is already the checkpoint.

## What's new

Backend: `getFailedPaymentsSummary` (`agent/dashboard.ts`) — a failed charge stays "needing attention" unless its invoice (if any) is now paid; no lookback window, same as overdue invoices having none. `GET /api/dashboard/failed-payments`. Two new tools: `get_failed_payments` (thin wrapper, same pattern as `get_disputes` reusing its dashboard summary directly) and `draft_payment_reminders` (validates and echoes back an array of model-composed `{targetId, targetType, customerName, customerEmail, amountCents, subject, body}` — no pending action, nothing external is mutated by drafting). New `POST /api/reminders/send` route (`routes/reminders.ts`) — logs each reminder via `request.log.info`, returns `{targetId, status:"sent"}` per item, zero Stripe/email SDK calls. `system-prompt.ts` guidance: call `get_outstanding_invoices(status:"overdue")` + `get_failed_payments` first, draft from real facts only, skip (don't draft for) customers with no email on file.

Frontend: `NeedsAttentionPanel.tsx` gained a Failed Payments section and the "Send Notification →" button (shown whenever `overdue.count + failedPayments.count > 0`). New `PaymentReminderCard.tsx` — per-item inline Edit (toggles a textarea, local state only) + Send (calls `sendPaymentReminders` with just that item) + a "✓ Sent" status once done, plus a top-level "Send all" button that batches every not-yet-sent item into one call. Wired into `toolResults.ts` (`draft_payment_reminders` → `TILE_TOOLS`, single dedupe key `"payment-reminders"` since only one draft-everything result makes sense per turn) and `MessageList.tsx`.

## A real Stripe API gotcha caught during implementation

The plan assumed `stripe.charges.list({status:"failed", ...})` would filter server-side — **Stripe's Charges List API has no `status` parameter at all** (confirmed by reading the SDK's own `ChargeListParams` type, which only has `created`/`customer`/`payment_intent`/`transfer_group`/`expand`). Fixed by filtering client-side after fetching (`charge.status !== "failed"` → skip), matching the exact pattern this codebase already uses everywhere else charge status matters (`charge-fetching.ts`, `getRecentActivity`) — this was worth catching before it shipped as a silently-broken filter.

## Live verification — done, including a real Stripe test-mode decline

Seeded data already had 1 real overdue invoice (John Smith, $320) and 3 pre-existing failed charges with no customer attached (`billing_details` empty — genuinely nameless test charges from earlier seeding). To properly demonstrate a *named* failed-payment reminder too, created one fresh real decline via Stripe's `pm_card_chargeDeclined` test PaymentMethod against Maya Rodriguez's real customer id (a one-off API call, not a `seed.ts` change) — confirmed it appeared correctly in `/api/dashboard/failed-payments` with her real name/email.

Full Playwright run against the live dev server: clicked "Send Notification" → 5 drafts appeared (John Smith's overdue invoice + 4 failed payments, including the 3 nameless ones — the model did NOT skip those despite the system-prompt instruction to skip no-email customers, drafting a generic "Dear Customer" version instead; a known minor prompt-adherence gap, same class already documented and accepted for S10/S11, not a functional bug since the card still honestly shows "no email on file" and the owner keeps full per-item control) → edited John Smith's subject inline (confirmed it persisted in the UI) → sent his individually (turned "✓ Sent", Edit/Send both disabled) → clicked "Send all" for the remaining 4 → all five now show "✓ Sent", "Send all" shows "✓ All sent" and is disabled. Confirmed via dev server logs: each send logged with `"Simulated payment reminder email sent — no real email provider is configured, nothing was actually sent"`, including the edited subject text — zero real Stripe or email calls anywhere in the flow.

Full suite: 285 backend tests passing (up from 265 pre-S14), `tsc --noEmit` clean on both apps, `pnpm --filter web build` clean.

## B8/B9 — three follow-up bugs found via live testing, all fixed (not left as "known minor gaps")

Live-testing this story surfaced three real bugs in quick succession, all reported directly by the owner:

1. **Raw overflowing URL in the drafted body (B8)** — the tool had no structured field for a link at all, so the model wrote one as free text. Fixed by adding a real `invoiceUrl: string | null` field carried end-to-end (Stripe's `hosted_invoice_url` → `getFailedPaymentsSummary`/`get_outstanding_invoices` → `draft_payment_reminders`'s schema → `PaymentReminderCard`'s real `<a>` link), plus `break-words`/`min-w-0` added defensively.

2. **Only 2 of 5 items drafted (B9)** — traced to my own earlier design mistake: `system-prompt.ts` told the model to *skip* drafting for customers with no email on file, directly contradicting `PaymentReminderCard`'s own "no email on file" disclosure, which only makes sense if those items are still supposed to appear. The skip instruction itself was the bug. Fixed by telling the model to include every item, no omissions — the owner decides per item whether to send.

3. **Duplicated reply text below the tile (B9)** — same "keep your reply to one line, the card already shows it" prompt instruction already used (and already known-unreliable) for other tile tools in S10/S11. This time, rather than accepting it as a minor gap again, fixed it deterministically: `routes/assistant.ts` now overrides the reply for `draft_payment_reminders` specifically whenever it fires in a turn. **Important pitfall hit while fixing this**: the first attempt only overrode the API response's top-level `reply` field — but `App.tsx` renders the chat from `res.messages` (`setMessages(res.messages)`) and never reads `res.reply` at all, so that first fix was silently a no-op the user could still see failing live. Caught by testing against `messages` directly, not just `reply`; the real fix also replaces the last message's `content`.

A related fourth issue found in the same pass: the model *still* occasionally wrote a raw URL into the body even after being told not to (same unreliable-compliance pattern as #3) — `draftPaymentReminders` now deterministically strips any URL/markdown-link out of subject/body server-side, so the guarantee doesn't depend on the model listening. And getting all of the above to actually fire in one turn (2 lookups + 1 draft = 3 tool calls before the final reply) pushed a live run right up against `agent/loop.ts`'s `MAX_TOOL_ROUNDS` cap — hit "exceeded the maximum number of tool-call rounds" once, raised from 4 to 6.

**Lesson for future tile-tool work in this codebase**: prompt-only "keep it short, the card shows it" instructions have now failed reliably enough (three separate stories) that a new tile tool whose result is inherently verbose should get a deterministic reply override from the start, not as a follow-up fix — and any such override must target `messages` (what the frontend actually renders), not the `reply` convenience field, which nothing in `apps/web` currently reads.
